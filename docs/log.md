## Phase 2 — Authentication System

Firebase (email/password + Google) as identity provider; backend verifies the Firebase ID token and mints its own JWT session (httpOnly access + refresh cookies) so RBAC is backend-owned and independent of Firebase's 1-hour token expiry. `ADMIN_EMAILS` env var auto-promotes matching accounts to admin on first sign-in. Frontend: Login/Register/Forgot-password forms, `useCurrentUser()` (TanStack Query) as source of truth with a thin Zustand mirror for route guards, axios interceptor for silent token refresh.

Mid-phase, scope expanded: user asked for self-service profile CRUD, customer order/cart visibility, and admin user-role management. Resolved by splitting the work — self-service profile CRUD (`PATCH/DELETE /users/me` + a My Profile page) landed in this phase since it's tightly coupled to the User model already being built; admin user-management (list/search/role-change) deferred to Phase 10 alongside the admin UI that will consume it, since shipping the API without a UI to exercise it means shipping untested surface area.

**Bug found and fixed (real security issue):** `PATCH /users/me` allowed a logged-in customer to smuggle `"role": "admin"` into the request body and self-promote. Root cause: the `validate()` middleware stripped unknown fields from the *validated Zod result* but never removed them from `req.body` itself, so the untouched `role` field rode along into the database write. Fixed at the middleware level (body fully replaced with validated data, not merged) and with defense-in-depth in the controller (explicit field whitelist rather than trusting `req.body` wholesale). Verified closed by retesting the exact attack.

## Phase 3 — Database Models, Seed Script, Cloudinary, Product/Brand/Category CRUD

## Phase 7 — Cart System

`Cart` module with atomic stock-validated add/update/remove and a `merge` endpoint. Totals computed from the *live* populated product price at fetch time, not the stored `priceSnapshot` — a cart is pre-purchase browsing state, so totals should reflect current reality; the snapshot only powers a "price changed" hint. Full stock-validation lifecycle verified via curl: add succeeds up to stock, exceeding stock is rejected with a clear message, merge caps at available stock rather than double-adding.

## Phase 8 — Checkout, Orders, Emails, Confirmation

The largest phase to date. New backend modules: `Address` (CRUD, first address auto-defaults, deleting the default promotes the next one), `Coupon` (model + `validate` endpoint, discount math centralized in `coupon.service.js` so preview and checkout can never drift — admin CRUD UI still deferred to Phase 10, seeded two real test coupons so checkout could actually be exercised), `InventoryLog` (audit trail for every stock movement), and `Order` itself.

**Stock reservation design** (the core of this phase): `reservedStock` holds inventory for pending orders without touching `stock`; crossing into a "committed" status (`confirmed` and beyond) converts the hold into a permanent `stock` decrement; cancelling before that commit just releases the hold, cancelling after restores the stock. Implemented inside a real MongoDB multi-document transaction (Atlas free-tier clusters are replica sets, so transactions are available) rather than best-effort sequential updates, since inventory/money correctness isn't a place to cut corners. Verified end-to-end via curl: reserve → confirm (commits stock) → cancel-after-confirm (restores stock) → separate order pending → cancel-before-confirm (releases hold, stock untouched) → terminal-status guard (can't modify a cancelled order further). All four paths behaved exactly as designed.

Before starting, asked the user whether to wire up bKash now or ship COD-only — chose COD-only given bKash needs real sandbox merchant credentials tied to a business account the user doesn't have yet. The `Order` schema already carries the bKash-related fields, so this is additive later, not a rework.

Frontend: Address book (inline add-new during checkout), Checkout page (address selection, phone/delivery note, coupon apply with live discount preview, COD-only payment selection with bKash shown disabled as "coming soon"), order confirmation page (success banner on first view, doubles as the permanent order-detail view), My Orders history list.

## Phase 8 bugfix — nested `<form>` elements broke coupon apply and address save

User reported that clicking "Apply" on the coupon field behaved like a page reload, and that saved addresses/customer details went missing on reload. Audited every form in the checkout flow to find the root cause: `CheckoutPage` wraps the whole checkout in one outer `<form>`, and both `AddressForm` (rendered via `AddressSelector`) and `CouponInput` rendered their *own* `<form>` elements inside it. HTML explicitly forbids `<form>` as a descendant of `<form>` — React will still construct that DOM structure without complaint, but the browser's `submit` event bubbles regardless, so clicking "Apply" or "Save address" fired the inner form's own handler *and* bubbled up to trigger the outer checkout form's `handleSubmit`, running full checkout validation/submission with whatever partial state happened to exist. Which of the two nested forms actually "owns" a given submit click is undefined behavior in browsers precisely because nested forms are invalid — that's why the symptoms looked inconsistent rather than a clean, reproducible failure.

Confirmed via the Phase 8 curl testing that `POST /addresses` itself was never the problem — this was purely a frontend structural bug, not data loss on the backend.

**Fix:** removed the `<form>` tag from both `AddressForm` and `CouponInput`, converting their submit buttons to `type="button"` with `onClick={handleSubmit(onSubmit)}` (react-hook-form's `handleSubmit` works fine as a plain click handler, it doesn't require an actual form submit event) — `CouponInput` additionally handles Enter-key-in-input manually via `onKeyDown` to restore the UX a real form would give for free. Audited every other `onSubmit={handleSubmit(...)}` usage in the codebase (8 total) for the same pattern — the only other candidate, `SimpleCatalogManager`'s form, lives inside a Radix `Dialog`, which portals its content to `document.body` and is therefore never actually a DOM descendant of any surrounding page form, so it was already safe.

Triggered by the user noticing their own real checkout ("order flow is incomplete i dont see a confirmed order in admin dashboard") — confirmed this was expected Phase 9 scope, not a Phase 8 gap, and proceeded.

**Backend:** `Order` gained `statusHistory[]` (status/note/changedBy/at — already existed structurally but is now populated on every transition), plus `trackingNumber`/`courierName`, settable when an admin transitions an order to `shipped`. `transitionOrderStatus` (the existing stock-reservation-aware service from Phase 8) extended to accept and persist them rather than adding a second write path. New admin endpoints: `GET /admin/orders/:id` (populates customer name/email/phone) and search-by-`orderNumber` (`?q=`) on the existing list endpoint.

Customer `OrderDetailPage` (from Phase 8) updated to render the same stepper and a tracking-number display block when present.

Admin Dashboard (previously a Phase 1 placeholder) rebuilt with real data: stat cards (today's revenue/orders, last-7-days revenue/orders, new customers today, low-stock count) and a hand-built SVG revenue line/area chart (no charting library in the stack, and a single-series daily-revenue chart doesn't justify adding one) with hover crosshair + tooltip, following the project's dataviz conventions — one hue since it's a single series (brand primary lime, no legend needed), thin 2px line, recessive gridlines. A top-products-today list rounds out the dashboard, linking each product through to its admin edit page.

Wired `/admin/orders` and `/admin/orders/:id` into the router (aliased imports since the customer-facing `OrdersPage`/`OrderDetailPage` names were already taken) and added an "Orders" entry to the admin sidebar nav.

## Phase 9 bugfix — order confirmation email never sent (real bug, user-reported)

User placed a real order from a logged-in customer account and got no confirmation email. Backend log showed the actual failure: `Order confirmation email failed: Resend: Missing \`to\` field.` Root cause: `authenticate` middleware deliberately keeps the JWT payload minimal — `req.user = { id, role} }` only, no name/email, to keep the token small and avoid baking in stale profile data. `createOrder` was passing `req.user` straight into `sendOrderConfirmationEmail`, which needs `.name`/`.email` for the `to` field and greeting — both were always `undefined` on that path. This bug existed since Phase 8 but was never caught because Phase 8's email verification called `sendOrderConfirmationEmail` directly with a hand-built fake user object (real name/email), never through the actual authenticated order-creation controller.

**Fix:** `createOrder` now fetches the real `User` document (`User.findById(req.user.id).select("name email")`) before sending, and passes that to the email function instead of the minimal JWT-derived `req.user`. Verified by fetching the real customer's account this way and sending an actual order-confirmation email end-to-end — delivered successfully, confirming the fix.

## Phase 12 (in progress) — Security hardening

Began Phase 12 with a security audit of the backend at the user's request. The existing posture was already strong (Firebase-verified identity, backend-owned JWT with DB-derived roles re-checked on refresh, `isActive` enforcement, boot-time length validation of all secrets, `costPrice` behind admin-only `select:+costPrice`, NoSQL-operator stripping, 10kb body caps, a scoped 20-req/15min auth rate-limiter, httpOnly/secure/sameSite cookies). Two real fixes applied:

- **`trust proxy` was unset** — a deployment-blocker, not a style nit. Behind Render/Railway's reverse proxy, Express would have seen the internal HTTP hop and silently refused to set `secure` cookies (breaking login entirely in production), and `express-rate-limit` would have keyed every request off the proxy's single IP (collapsing all users into one bucket). Added `app.set("trust proxy", 1)` gated on production — deliberately `1` (one known hop), not `true`, since trusting all hops lets a client spoof `X-Forwarded-For` to dodge IP rate limiting.
- **Admin auto-promotion didn't require a verified email** — `findOrCreateUser` promoted any account whose email matched `ADMIN_EMAILS`, but the Firebase token was only checked for validity, not `email_verified`. Firebase does not require email verification for email/password sign-ups by default, so this was a (narrow, since the real admin address is already a registered Firebase account) self-escalation path. Now gated on `email_verified === true`; Google sign-ins are always verified so the normal admin path is unaffected.

Both verified against a clean backend boot.

**Refresh-token versioning + rotation (implemented after the user asked for it):** added a `tokenVersion` counter to the `User` model, stamped into every JWT as `tv`. The refresh path (which already re-fetched the user from the DB) now also rejects any refresh token whose `tv` doesn't match the account's current value, and rotates *both* tokens on each refresh instead of only re-issuing the access token. `tokenVersion` is bumped on self-deactivation, admin deactivation, and role change — so a ban or demotion kills the account's outstanding sessions immediately rather than waiting out the 30-day refresh token. Deliberately kept the access-token check stateless (no per-request DB hit): the ≤15-min access window is unchanged, but the long-lived refresh credential is now instantly revocable, which is where the real risk lived. No new infrastructure, env vars, or frontend changes — tokens live in httpOnly cookies the client never touches, and an invalidated session degrades through the existing axios refresh-interceptor → login redirect. The one transition effect (existing sessions carry no `tv` claim and get logged out once) is a non-event pre-launch. Removed the now-unused `setAccessTokenCookie` cookie helper. Verified end-to-end against a disposable test user: matching version rotates (200 + fresh refresh cookie), a stale token after a version bump is rejected (401), and a fresh token at the new version works again (200).

Remaining audit items are documented recommendations, not bugs — a shared rate-limit store (only matters past one server instance) and confirming Firebase's email-enumeration protection is on in the console before launch.

## Phase 12 bugfix — auth retry-storm locked users out of login (user-reported)

Verifying the code-split flow surfaced a real bug the Phase 12 `tokenVersion` change had exposed: after `tokenVersion` invalidated the user's pre-existing session, the frontend couldn't log in — `/auth/session` returned 429. Two latent weaknesses combined:

1. **Login and refresh shared one rate-limit budget** (`authLimiter`, 20 req/15min on both `/auth/session` and `/auth/refresh`). When the invalidated session made `/auth/refresh` fail, the client retried it enough to exhaust that shared budget — which also blocked `/auth/session`, i.e. the one path that recovers a broken session.
2. **The axios refresh interceptor had no failure backoff** — every component/route reading the current user on load fired its own 401 → refresh, and on a page with several such reads that storms the endpoint.

Fixes: (a) split the rate limiter into a tight `loginLimiter` (20/15min, brute-force protection on user-initiated login) and a separate, more forgiving `refreshLimiter` (60/15min) so a refresh problem can never lock out login again; (b) added a 10-second cooldown in the interceptor after a *failed* refresh, so subsequent 401s settle into a logged-out state instead of hammering `/auth/refresh` (a *successful* refresh never triggers the cooldown, so normal token renewal is unaffected). Restarted the backend to clear the exhausted in-memory limiter. Verified: `/auth/session` and `/auth/refresh` return 401 (not 429) after restart, and the user confirmed login works with only the expected single `/auth/me`+`/auth/refresh` bootstrap pair on load — no storm. (The residual console noise the user asked about is all benign: a browser ad-blocker extension's `content-script.js`, the expected logged-out auth-probe 401s, and Firebase's well-known COOP `window.closed` popup warning — the last to be silenced in production via a `Cross-Origin-Opener-Policy: same-origin-allow-popups` header on the frontend host.)

## System 7 — Order Management (unrestricted status changes, symmetric stock handling)

The highest-risk system in this whole batch — it rewrites the transaction-protected stock-reservation state machine every checkout, confirm, and cancel already depends on. Treated with the most thorough verification of any system so far, per the architecture review's own instruction.

**Redesigned `transitionOrderStatus` as a proper 3-bucket state machine**, not a patch on the original binary `wasCommitted`/`willBeCommitted` model. Every order status maps to exactly one stock bucket: `reserved` (pending — held via `reservedStock`, nothing decremented), `committed` (confirmed/packed/shipped/delivered — `stock` permanently decremented, no hold), `released` (cancelled/refunded — no claim on stock at all). The terminal lock (`if (TERMINAL_STATUSES.includes(order.status)) throw`) is gone entirely — the only remaining guard is same-status. All six possible cross-bucket moves are now handled explicitly; same-bucket moves (`confirmed → packed`, `cancelled → refunded`) are pure status-label changes with no stock effect, same as before.

**Two real design errors caught before writing any code, by working through concrete numbers by hand:**
1. The architecture review's own plan text for the `committed → reserved` delta (reverting e.g. `confirmed → pending`) was wrong: it said `{stock: -qty, reservedStock: +qty}`. Tracing through actual numbers (stock=10 → reserve 2 → confirm → stock=8,reserved=0 → revert) showed this would leave `availableStock` incorrectly lower after every revert, silently drifting the whole product's numbers wrong on repeated confirm/revert cycles. The correct delta restores *both* fields: `{stock: +qty, reservedStock: +qty}` — undoes the sale and re-establishes the hold, leaving `availableStock` exactly where it was.
2. The review never accounted for reverting *out of* a released status at all (`cancelled`/`refunded → anything else`) — a real gap, since a released order's hold has already been fully cleared to zero, so naively reusing the reserved→committed branch for that direction would drive `reservedStock` negative.

**`released → reserved` and `released → committed` are the only two directions that re-check stock availability** before applying their delta, using the same atomic `findOneAndUpdate` + `$expr` compare-and-reserve pattern `reserveStockForItems` already uses for checkout. Every other direction trusts the order's existing hold/commit and applies its delta unconditionally, same as the original code. This isn't precautionary — another customer can genuinely buy up stock while an order sits cancelled, and un-cancelling it without a fresh check would oversell.

**Frontend.** Admin `OrderDetailPage.jsx`'s `isTerminal` guard (which hid the "Update Status" form once an order reached `cancelled`/`refunded`) is deleted — the form is now always shown. The existing `STATUS_OPTIONS.filter((s) => s !== order.status)` line is untouched, so "change to the same status" still can't be selected.

**Verified via a curl-scripted transition matrix against a real product on the dev database** (not mocked/unit-tested state) — 24 assertions, all passing: all six cross-bucket transitions with exact `stock`/`reservedStock` checks after every hop (`pending → delivered → pending → confirmed → refunded → shipped → refunded → pending → cancelled → refunded`), the same-bucket no-op (`cancelled → refunded`), the same-status guard, and the exact `confirmed → pending → cancelled` sequence independently flagged during the architecture review as a real latent bug in the pre-System-7 code (confirmed closed — `reservedStock` no longer goes negative). Also verified the new availability guard actually rejects an unsafe revert: cancelled a 4-unit order, let a second real order consume all 4 freed units, then confirmed the first order's attempt to un-cancel correctly 409s instead of silently overselling. All test orders and their inventory logs deleted afterward; the product restored to its exact original `stock`/`reservedStock` baseline.

Also added a Vitest unit test for `stockBucket()` (now exported), the pure classification function every transition branch dispatches on — the `$inc`/atomic-guard mutation logic itself stays curl-verified rather than introducing new integration-test infrastructure (e.g. `mongodb-memory-server`), consistent with how every other transaction-heavy path in this project has been verified.

Both production builds clean, all 35 backend tests (32 existing + 3 new) and 11 frontend tests still green.

Solved with DaisyUI multi-theme + a second `data-theme` scope: `:root` now holds the new light values (paper `#FAFAF7` background, ink `#101208` foreground, lime `#A8CD2F` primary, Archivo display font, Instrument Sans body font) as the unscoped default, and a new `[data-theme="diecastbd-admin"]` block re-declares every one of those same custom properties back to their exact pre-redesign dark values (`#0a0a0a`/`#a3e635`/Geist Variable). `AdminLayout.jsx`'s root `<div>` gained `data-theme="diecastbd-admin"` — the one-line change that's the entire mechanism, since every existing admin component already reads these custom properties and neither knows nor cares which scope supplied them. Two DaisyUI themes (`diecastbd` --default, `diecastbd-admin`) registered the same way, so the DaisyUI-only components (Rating/Steps/Loading, shared by both admin and storefront) pick up the correct palette automatically too. `--sidebar-*` tokens were left unscoped/untouched at their original dark values — only `AdminLayout`'s sidebar ever reads them, so there's nothing to preserve-by-duplication there.

Archivo (500/600/700/800 + italics) and Instrument Sans (400–700) loaded via Google Fonts CSS2 in `index.html` (`preconnect` + one `<link>`, `display=swap`), alongside a `theme-color` meta update (`#0a0a0a` → `#FAFAF7`). Caught one naming mistake before it shipped: initially wrote `--display-font: "Archivo Variable", ...` (Fontsource npm-package convention), but these are loaded via Google Fonts CSS2, not Fontsource, so the registered family name is plain `"Archivo"` — fixed before testing.

**Verified with a real headless browser** (Playwright, installed fresh into the sandbox — none was pre-available), not just a clean build: launched the dev server, screenshotted the actual homepage (confirms the light paper background, lime buttons, and lime DaisyUI loading spinner all render correctly with no code changes beyond tokens) and the login page (`AuthLayout`, also in-scope for the redesign — same light theme, correct). Directly verified the admin-scoping mechanism itself by injecting a `data-theme="diecastbd-admin"` wrapper via `page.evaluate` and reading back the computed custom-property values — confirmed byte-identical to the original dark theme (`background:#0a0a0a`, `primary:#a3e635`, `font:"Geist Variable"`) versus the unscoped page's new values, proving the CSS cascade mechanism works independent of React routing. Also navigated to `/admin` directly (redirects to `/login` when unauthenticated, as expected) and checked for console errors — only the two expected 401s from the pre-existing unauthenticated session-check calls, no regressions.
