## Phase 2 — Authentication System

Firebase (email/password + Google) as identity provider; backend verifies the Firebase ID token and mints its own JWT session (httpOnly access + refresh cookies) so RBAC is backend-owned and independent of Firebase's 1-hour token expiry. `ADMIN_EMAILS` env var auto-promotes matching accounts to admin on first sign-in. Frontend: Login/Register/Forgot-password forms, `useCurrentUser()` (TanStack Query) as source of truth with a thin Zustand mirror for route guards, axios interceptor for silent token refresh.

Mid-phase, scope expanded: user asked for self-service profile CRUD, customer order/cart visibility, and admin user-role management. Resolved by splitting the work — self-service profile CRUD (`PATCH/DELETE /users/me` + a My Profile page) landed in this phase since it's tightly coupled to the User model already being built; admin user-management (list/search/role-change) deferred to Phase 10 alongside the admin UI that will consume it, since shipping the API without a UI to exercise it means shipping untested surface area.

**Bug found and fixed (real security issue):** `PATCH /users/me` allowed a logged-in customer to smuggle `"role": "admin"` into the request body and self-promote. Root cause: the `validate()` middleware stripped unknown fields from the *validated Zod result* but never removed them from `req.body` itself, so the untouched `role` field rode along into the database write. Fixed at the middleware level (body fully replaced with validated data, not merged) and with defense-in-depth in the controller (explicit field whitelist rather than trusting `req.body` wholesale). Verified closed by retesting the exact attack.

## Phase 3 — Database Models, Seed Script, Cloudinary, Product/Brand/Category CRUD

## Phase 7 — Cart System

`Cart` module with atomic stock-validated add/update/remove and a `merge` endpoint. Totals computed from the *live* populated product price at fetch time, not the stored `priceSnapshot` — a cart is pre-purchase browsing state, so totals should reflect current reality; the snapshot only powers a "price changed" hint. Full stock-validation lifecycle verified via curl: add succeeds up to stock, exceeding stock is rejected with a clear message, merge caps at available stock rather than double-adding.

## Phase 8 — Checkout, Orders, Emails, Confirmation

The largest phase to date. New backend modules: `Address` (CRUD, first address auto-defaults, deleting the default promotes the next one), `Coupon` (model + `validate` endpoint, discount math centralized in `coupon.service.js` so preview and checkout can never drift — admin CRUD UI still deferred to Phase 10, seeded two real test coupons so checkout could actually be exercised), `InventoryLog` (audit trail for every stock movement), and `Order` itself.

**Stock reservation design** (the core of this phase): `reservedStock` holds inventory for pending orders without touching `stock`; crossing into a "committed" status (`confirmed` and beyond) converts the hold into a permanent `stock` decrement; cancelling before that commit just releases the hold, cancelling after restores the stock. Implemented inside a real MongoDB multi-document transaction (Atlas free-tier clusters are replica sets, so transactions are available) rather than best-effort sequential updates, since inventory/money correctness isn't a place to cut corners. Verified end-to-end via curl: reserve → confirm (commits stock) → cancel-after-confirm (restores stock) → separate order pending → cancel-before-confirm (releases hold, stock untouched) → terminal-status guard (can't modify a cancelled order further). All four paths behaved exactly as designed.

Before starting, asked the user whether to wire up bKash now or ship COD-only — chose COD-only given bKash needs real sandbox merchant credentials tied to a business account the user doesn't have yet. The `Order` schema already carries the bKash-related fields, so this is additive later, not a rework.

Frontend: Address book (inline add-new during checkout), Checkout page (address selection, phone/delivery note, coupon apply with live discount preview, COD-only payment selection with bKash shown disabled as "coming soon"), order confirmation page (success banner on first view, doubles as the permanent order-detail view), My Orders history list.

## Phase 8 bugfix — nested `<form>` elements broke coupon apply and address save

User reported that clicking "Apply" on the coupon field behaved like a page reload, and that saved addresses/customer details went missing on reload. Audited every form in the checkout flow to find the root cause: `CheckoutPage` wraps the whole checkout in one outer `<form>`, and both `AddressForm` (rendered via `AddressSelector`) and `CouponInput` rendered their *own* `<form>` elements inside it. HTML explicitly forbids `<form>` as a descendant of `<form>` — React will still construct that DOM structure without complaint, but the browser's `submit` event bubbles regardless, so clicking "Apply" or "Save address" fired the inner form's own handler *and* bubbled up to trigger the outer checkout form's `handleSubmit`, running full checkout validation/submission with whatever partial state happened to exist. Which of the two nested forms actually "owns" a given submit click is undefined behavior in browsers precisely because nested forms are invalid — that's why the symptoms looked inconsistent rather than a clean, reproducible failure.

Confirmed via the Phase 8 curl testing that `POST /addresses` itself was never the problem — this was purely a frontend structural bug, not data loss on the backend.

**Fix:** removed the `<form>` tag from both `AddressForm` and `CouponInput`, converting their submit buttons to `type="button"` with `onClick={handleSubmit(onSubmit)}` (react-hook-form's `handleSubmit` works fine as a plain click handler, it doesn't require an actual form submit event) — `CouponInput` additionally handles Enter-key-in-input manually via `onKeyDown` to restore the UX a real form would give for free. Audited every other `onSubmit={handleSubmit(...)}` usage in the codebase (8 total) for the same pattern — the only other candidate, `SimpleCatalogManager`'s form, lives inside a Radix `Dialog`, which portals its content to `document.body` and is therefore never actually a DOM descendant of any surrounding page form, so it was already safe.

Triggered by the user noticing their own real checkout ("order flow is incomplete i dont see a confirmed order in admin dashboard") — confirmed this was expected Phase 9 scope, not a Phase 8 gap, and proceeded.

**Backend:** `Order` gained `statusHistory[]` (status/note/changedBy/at — already existed structurally but is now populated on every transition), plus `trackingNumber`/`courierName`, settable when an admin transitions an order to `shipped`. `transitionOrderStatus` (the existing stock-reservation-aware service from Phase 8) extended to accept and persist them rather than adding a second write path. New admin endpoints: `GET /admin/orders/:id` (populates customer name/email/phone) and search-by-`orderNumber` (`?q=`) on the existing list endpoint.

Customer `OrderDetailPage` (from Phase 8) updated to render the same stepper and a tracking-number display block when present.

Admin Dashboard (previously a Phase 1 placeholder) rebuilt with real data: stat cards (today's revenue/orders, last-7-days revenue/orders, new customers today, low-stock count) and a hand-built SVG revenue line/area chart (no charting library in the stack, and a single-series daily-revenue chart doesn't justify adding one) with hover crosshair + tooltip, following the project's dataviz conventions — one hue since it's a single series (brand primary lime, no legend needed), thin 2px line, recessive gridlines. A top-products-today list rounds out the dashboard, linking each product through to its admin edit page.

Wired `/admin/orders` and `/admin/orders/:id` into the router (aliased imports since the customer-facing `OrdersPage`/`OrderDetailPage` names were already taken) and added an "Orders" entry to the admin sidebar nav.

## Phase 9 bugfix — order confirmation email never sent (real bug, user-reported)

User placed a real order from a logged-in customer account and got no confirmation email. Backend log showed the actual failure: `Order confirmation email failed: Resend: Missing \`to\` field.` Root cause: `authenticate` middleware deliberately keeps the JWT payload minimal — `req.user = { id, role} }` only, no name/email, to keep the token small and avoid baking in stale profile data. `createOrder` was passing `req.user` straight into `sendOrderConfirmationEmail`, which needs `.name`/`.email` for the `to` field and greeting — both were always `undefined` on that path. This bug existed since Phase 8 but was never caught because Phase 8's email verification called `sendOrderConfirmationEmail` directly with a hand-built fake user object (real name/email), never through the actual authenticated order-creation controller.

**Fix:** `createOrder` now fetches the real `User` document (`User.findById(req.user.id).select("name email")`) before sending, and passes that to the email function instead of the minimal JWT-derived `req.user`. Verified by fetching the real customer's account this way and sending an actual order-confirmation email end-to-end — delivered successfully, confirming the fix.

## Phase 12 (in progress) — Security hardening

Began Phase 12 with a security audit of the backend at the user's request. The existing posture was already strong (Firebase-verified identity, backend-owned JWT with DB-derived roles re-checked on refresh, `isActive` enforcement, boot-time length validation of all secrets, `costPrice` behind admin-only `select:+costPrice`, NoSQL-operator stripping, 10kb body caps, a scoped 20-req/15min auth rate-limiter, httpOnly/secure/sameSite cookies). Two real fixes applied:

- **`trust proxy` was unset** — a deployment-blocker, not a style nit. Behind Render/Railway's reverse proxy, Express would have seen the internal HTTP hop and silently refused to set `secure` cookies (breaking login entirely in production), and `express-rate-limit` would have keyed every request off the proxy's single IP (collapsing all users into one bucket). Added `app.set("trust proxy", 1)` gated on production — deliberately `1` (one known hop), not `true`, since trusting all hops lets a client spoof `X-Forwarded-For` to dodge IP rate limiting.
- **Admin auto-promotion didn't require a verified email** — `findOrCreateUser` promoted any account whose email matched `ADMIN_EMAILS`, but the Firebase token was only checked for validity, not `email_verified`. Firebase does not require email verification for email/password sign-ups by default, so this was a (narrow, since the real admin address is already a registered Firebase account) self-escalation path. Now gated on `email_verified === true`; Google sign-ins are always verified so the normal admin path is unaffected.

Both verified against a clean backend boot.

**Refresh-token versioning + rotation (implemented after the user asked for it):** added a `tokenVersion` counter to the `User` model, stamped into every JWT as `tv`. The refresh path (which already re-fetched the user from the DB) now also rejects any refresh token whose `tv` doesn't match the account's current value, and rotates *both* tokens on each refresh instead of only re-issuing the access token. `tokenVersion` is bumped on self-deactivation, admin deactivation, and role change — so a ban or demotion kills the account's outstanding sessions immediately rather than waiting out the 30-day refresh token. Deliberately kept the access-token check stateless (no per-request DB hit): the ≤15-min access window is unchanged, but the long-lived refresh credential is now instantly revocable, which is where the real risk lived. No new infrastructure, env vars, or frontend changes — tokens live in httpOnly cookies the client never touches, and an invalidated session degrades through the existing axios refresh-interceptor → login redirect. The one transition effect (existing sessions carry no `tv` claim and get logged out once) is a non-event pre-launch. Removed the now-unused `setAccessTokenCookie` cookie helper. Verified end-to-end against a disposable test user: matching version rotates (200 + fresh refresh cookie), a stale token after a version bump is rejected (401), and a fresh token at the new version works again (200).

Remaining audit items are documented recommendations, not bugs — a shared rate-limit store (only matters past one server instance) and confirming Firebase's email-enumeration protection is on in the console before launch.

## Phase 12 bugfix — auth retry-storm locked users out of login (user-reported)

Verifying the code-split flow surfaced a real bug the Phase 12 `tokenVersion` change had exposed: after `tokenVersion` invalidated the user's pre-existing session, the frontend couldn't log in — `/auth/session` returned 429. Two latent weaknesses combined:

1. **Login and refresh shared one rate-limit budget** (`authLimiter`, 20 req/15min on both `/auth/session` and `/auth/refresh`). When the invalidated session made `/auth/refresh` fail, the client retried it enough to exhaust that shared budget — which also blocked `/auth/session`, i.e. the one path that recovers a broken session.
2. **The axios refresh interceptor had no failure backoff** — every component/route reading the current user on load fired its own 401 → refresh, and on a page with several such reads that storms the endpoint.

Fixes: (a) split the rate limiter into a tight `loginLimiter` (20/15min, brute-force protection on user-initiated login) and a separate, more forgiving `refreshLimiter` (60/15min) so a refresh problem can never lock out login again; (b) added a 10-second cooldown in the interceptor after a *failed* refresh, so subsequent 401s settle into a logged-out state instead of hammering `/auth/refresh` (a *successful* refresh never triggers the cooldown, so normal token renewal is unaffected). Restarted the backend to clear the exhausted in-memory limiter. Verified: `/auth/session` and `/auth/refresh` return 401 (not 429) after restart, and the user confirmed login works with only the expected single `/auth/me`+`/auth/refresh` bootstrap pair on load — no storm. (The residual console noise the user asked about is all benign: a browser ad-blocker extension's `content-script.js`, the expected logged-out auth-probe 401s, and Firebase's well-known COOP `window.closed` popup warning — the last to be silenced in production via a `Cross-Origin-Opener-Policy: same-origin-allow-popups` header on the frontend host.)

## System 7 — Order Management (unrestricted status changes, symmetric stock handling)

The highest-risk system in this whole batch — it rewrites the transaction-protected stock-reservation state machine every checkout, confirm, and cancel already depends on. Treated with the most thorough verification of any system so far, per the architecture review's own instruction.

**Redesigned `transitionOrderStatus` as a proper 3-bucket state machine**, not a patch on the original binary `wasCommitted`/`willBeCommitted` model. Every order status maps to exactly one stock bucket: `reserved` (pending — held via `reservedStock`, nothing decremented), `committed` (confirmed/packed/shipped/delivered — `stock` permanently decremented, no hold), `released` (cancelled/refunded — no claim on stock at all). The terminal lock (`if (TERMINAL_STATUSES.includes(order.status)) throw`) is gone entirely — the only remaining guard is same-status. All six possible cross-bucket moves are now handled explicitly; same-bucket moves (`confirmed → packed`, `cancelled → refunded`) are pure status-label changes with no stock effect, same as before.

**Two real design errors caught before writing any code, by working through concrete numbers by hand:**
1. The architecture review's own plan text for the `committed → reserved` delta (reverting e.g. `confirmed → pending`) was wrong: it said `{stock: -qty, reservedStock: +qty}`. Tracing through actual numbers (stock=10 → reserve 2 → confirm → stock=8,reserved=0 → revert) showed this would leave `availableStock` incorrectly lower after every revert, silently drifting the whole product's numbers wrong on repeated confirm/revert cycles. The correct delta restores *both* fields: `{stock: +qty, reservedStock: +qty}` — undoes the sale and re-establishes the hold, leaving `availableStock` exactly where it was.
2. The review never accounted for reverting *out of* a released status at all (`cancelled`/`refunded → anything else`) — a real gap, since a released order's hold has already been fully cleared to zero, so naively reusing the reserved→committed branch for that direction would drive `reservedStock` negative.

**`released → reserved` and `released → committed` are the only two directions that re-check stock availability** before applying their delta, using the same atomic `findOneAndUpdate` + `$expr` compare-and-reserve pattern `reserveStockForItems` already uses for checkout. Every other direction trusts the order's existing hold/commit and applies its delta unconditionally, same as the original code. This isn't precautionary — another customer can genuinely buy up stock while an order sits cancelled, and un-cancelling it without a fresh check would oversell.

**Frontend.** Admin `OrderDetailPage.jsx`'s `isTerminal` guard (which hid the "Update Status" form once an order reached `cancelled`/`refunded`) is deleted — the form is now always shown. The existing `STATUS_OPTIONS.filter((s) => s !== order.status)` line is untouched, so "change to the same status" still can't be selected.

**Verified via a curl-scripted transition matrix against a real product on the dev database** (not mocked/unit-tested state) — 24 assertions, all passing: all six cross-bucket transitions with exact `stock`/`reservedStock` checks after every hop (`pending → delivered → pending → confirmed → refunded → shipped → refunded → pending → cancelled → refunded`), the same-bucket no-op (`cancelled → refunded`), the same-status guard, and the exact `confirmed → pending → cancelled` sequence independently flagged during the architecture review as a real latent bug in the pre-System-7 code (confirmed closed — `reservedStock` no longer goes negative). Also verified the new availability guard actually rejects an unsafe revert: cancelled a 4-unit order, let a second real order consume all 4 freed units, then confirmed the first order's attempt to un-cancel correctly 409s instead of silently overselling. All test orders and their inventory logs deleted afterward; the product restored to its exact original `stock`/`reservedStock` baseline.

Also added a Vitest unit test for `stockBucket()` (now exported), the pure classification function every transition branch dispatches on — the `$inc`/atomic-guard mutation logic itself stays curl-verified rather than introducing new integration-test infrastructure (e.g. `mongodb-memory-server`), consistent with how every other transaction-heavy path in this project has been verified.

Both production builds clean, all 35 backend tests (32 existing + 3 new) and 11 frontend tests still green.

## 2026-07-12 — Product images: explicit max-height/no-max-width/centered, at the user's direction, trading "never crop" for "never gap"

Same-day follow-up to decision #56. See plan.md §7 decision #57.

Even after #56 removed the baked-in square pad, small vertical gaps could still appear under `object-contain` whenever a card's box was proportionally wider than the photo — `contain` never lets an image exceed either box dimension, so a wide box paired with a 3:2/square photo can leave visible space beside or below it. The user posted a DevTools screenshot of an `img, video { max-height: 100%; ... }` rule and gave an explicit instruction: "In product image always use max-height 100% & remove any max width & image position will be always in center position."

Before implementing, I calculated and surfaced the trade-off: this approach guarantees the box's height is always filled (no gaps), but gives up #56's "never crop" guarantee — any box narrower than the photo's native aspect ratio will now crop the image's sides, since width is only bounded by the image's own (now height-driven) intrinsic scaling, not by the box. The user's answer was explicit: "do what i say." Implemented exactly as instructed.

**Change:** replaced each `cloudinaryCard()` consumer's image className with `mx-auto block max-h-full w-auto max-w-none` — height fills the box (`max-h-full`, box already has a definite height in every case), width auto-scales from the image's intrinsic ratio (`w-auto`, no `max-w-none` cap), `mx-auto` centers it horizontally, `block` avoids the inline-image baseline gap. Applied across all 9 call sites: `ProductCard` (grid+carousel), `WishlistCard`, `FeaturedSpotlight` (`Spotlight` + `RowCard`), `ProductGallery` (main image + thumbnail strip), `CartLineItem`, `CheckoutSummary`, `OrderReceipt`, `RestockAlertDialog`. `ProductGallery`'s separate full-res lightbox `<img>` was deliberately left on `object-contain` — it shows the whole image at its natural proportions rather than filling a fixed box, so the new pattern doesn't apply there. `cloudinaryCard()`'s `CARD_TRANSFORM` (`c_limit,w_800`) is untouched — this is a CSS-only change.

One edge case needed live verification rather than just reading the code: `CartLineItem`'s `Thumb` wraps the image in a `<Link>` (an `<a>`, which defaults to `display: inline` and would normally ignore height/width). Checked via `getComputedStyle` in the running preview (added a test item to the cart, navigated to `/cart`) and confirmed the anchor computes as `display: block` anyway, because it's always a direct child of a `flex` container in both the mobile and desktop rows — CSS blockifies flex/grid children regardless of their own specified display. No extra class was needed. Every other affected box is a plain `<div>` (block by default) with `overflow-hidden` on itself or a same-width ancestor, so any new horizontal overflow from `w-auto max-w-none` clips cleanly at the card's rounded corners instead of bleeding outside it.

**Verified:** `npm run lint` clean (pre-existing warnings only), `npm run build` clean, frontend `npm test` (17/17). Frontend-only, no backend/schema change, no redeploy needed — safe for the live deployment (needs a frontend rebuild to take effect).

**Same-day correction #1 — margin-auto doesn't center overflowing content:** the user then reported (via a ProductDetailPage screenshot of MINI GT #1106) that the image was anchored to the left edge with all cropping happening on the right side, not centered. This is a real CSS spec gotcha, not a fluke: per CSS2.1 §10.3.3, when a block box is *wider than its containing block*, `auto` margins resolve to `0` instead of splitting the overflow evenly — `margin: auto` can only center content that fits inside its box; it cannot center-crop overflowing content, which is what `mx-auto` was being asked to do once `max-w-none` let the image exceed its box width. Fixed by replacing `mx-auto block max-h-full w-auto max-w-none` with `size-full object-cover object-center` across all 9 call sites (same list as above). `object-fit: cover` fills a box with known width+height (`size-full`, valid since every parent box has a definite width — explicit or via flex-stretch — and a definite height) and `object-position: center` crops symmetrically from both sides instead of anchoring to one edge. This is the standards-based way to get "always fill the box, crop always centered," and matches the user's original ask precisely, without the margin-auto edge case. Verified again: `npm run lint` clean, `npm run build` clean, frontend `npm test` (17/17).

**Same-day correction #2 — `object-cover` was still cropping the height, not just the width:** the user posted a 3-card grid screenshot (Hot Wheels Premium blister packs: Cyberpunk 2077, Racing Bulls #6, Ferrari SF-25) and explained precisely: "I need full height should be view inside the product card... width could crop it's not matter about the width." These packaging photos are shot **portrait** (tall) while the card's image box is **landscape** (wide-short) — `object-fit: cover` derives one scale factor that satisfies *both* box dimensions at once, and for a portrait photo in a landscape box that factor is set by the box's width, which then over-scales the photo's height past the box, so `cover` crops it top/bottom. That's the opposite of "full height visible." Neither `cover` nor `contain` can express "pin height exactly, let width float and crop freely" — they always derive a single joint scale factor. Fixed by dropping `object-fit` entirely and using plain replaced-element sizing instead: the `<img>` gets `h-full w-auto max-w-none` (height locked to the box's own height; width auto-scales from the image's own intrinsic ratio, uncapped), and the parent box gains `flex items-center justify-center` alongside its existing `relative overflow-hidden` classes. The key trick: flexbox's `justify-content: center` correctly centers a child even when the child is *wider* than the flex container (excess splits evenly on both sides, clipped symmetrically by `overflow-hidden`) — unlike block-level `margin: auto`, which is exactly the bug fixed in correction #1. Applied across the same 9 call sites (`ProductCard` grid+carousel, `WishlistCard`, `FeaturedSpotlight` Spotlight+RowCard, `ProductGallery` main+thumbnails, `CartLineItem`, `CheckoutSummary`, `OrderReceipt`, `RestockAlertDialog`). Bonus: `CartLineItem`'s `Thumb` (`<Link>`/`<a>`) now declares `flex` directly, which makes the earlier flex-item-blockification reasoning moot — an explicit `display: flex` doesn't need help from being a flex child to become block-level. Verified: `npm run lint` clean, `npm run build` clean, frontend `npm test` (17/17).

**Same-day follow-up — taller `ProductCard` image box (300px desktop) now that height is the pinned/never-cropped axis:** with correction #2 locking height as always-fully-visible, the user asked to make the box itself taller so more of each (mostly portrait) product photo shows before width-cropping kicks in: "for carousel & store product card use 300px height for web same ratio increase the height for mobile as well." ### Admin: bulk-select + permanent delete for orders (2026-07-13)

Merchant wanted multi-select + delete + a confirmation modal on the admin orders list (theirs is full of test orders). Plan.md decision #74.

**This is not a UI feature — orders are stock-bearing.** No delete endpoint existed, and a bare `deleteMany` would have silently corrupted inventory: it's the decision-#8/#37 three-bucket problem approached from a new direction. A **pending** order holds a `reservedStock` hold; deleting it without releasing that hold leaks the reservation *forever* — `availableStock` quietly drops with no order left on the books to explain why. A **confirmed→delivered** order has already had its units decremented from `stock`. A **cancelled/refunded** order holds no claim at all.

So the semantics were put to the merchant rather than assumed. They chose **permanent delete, any status** (over "cancelled/refunded only" and soft-delete): delete means *"this order never happened"*. New `deleteOrders()` reuses the **same `stockBucket()` classifier** as `transitionOrderStatus` instead of re-deriving the rule — reserved → release the hold; committed → return the units; released → nothing to give back. Stock writes, `InventoryLog`, `AuditLog` and the `deleteMany` all run in **one transaction**, so a mid-flight failure can't adjust stock for an order that still exists.

Two details worth remembering: `InventoryLog.referenceOrder` is left null (the order it would point at is about to stop existing) with the order number written into `reason` instead; and the route deliberately skips the `auditLog()` middleware — it keys off a single `req.params.id` and can't snapshot each order in a bulk delete. `deleteOrders` writes a per-order audit entry carrying the **full order document**, which after the delete is the only surviving copy and doubles as the recovery path.

Selection resets on page/filter/search change so you can't delete a row you can no longer see.

**Verified:** 6 new RTL tests covering selection and the confirmation gate (including "opening the dialog must not delete" and that exactly the selected ids are sent), plus a committed real-DB regression script `backend/scripts/verify-order-delete.mjs` — it creates one order in each stock bucket, deletes all three, and asserts inventory lands exactly back on baseline: stock 12→12, reservedStock 2→2 (the pre-existing reservation from *other* orders correctly untouched), 3 units returned (1 reserved + 2 committed + 0 cancelled), and 3 recoverable audit snapshots. ## 2026-07-28 (later) — CartUp rejected the upload: payload_hidden was never computed

Merchant uploaded the generated xlsx and CartUp answered *"No products were found in your excel upload."* Root cause found and fixed.

**CartUp's importer reads `payload_hidden`, not the visible `product` sheet.** Every cell on that sheet is a formula — `=IF(product!A3<>"",product!A3,"")` for pass-through columns, `=IF(product!L3<>"", VLOOKUP(product!L3, product_attribute_1[#All],2,FALSE),"")` for the six dropdown columns. Formulas only acquire values when a spreadsheet application recalculates on save. The XML-surgery build (decision #82) never opens one, so all 19,500 payload cells shipped as formulas with **no cached value** — a server-side reader sees 19,500 blanks and concludes there are no products, however complete the visible sheet looks. Decision #82 had explicitly reasoned the opposite ("CartUp's importer almost certainly does NOT read payload_hidden's cached values — it can't, they'd never be valid"); that inference was wrong, and the upload error is the evidence.

**Fix:** `build_cartup_sheet.py` now computes the payload itself. `compute_payload()` derives each column's source and lookup table by parsing the row-2 formulas (no hard-coded column map — a template revision can't silently break it), resolves the six VLOOKUP columns against the `value_hidden` tables read from the workbook's own table definitions, and writes the results as cached `<v>` values beside the untouched `<f>`. Types follow Excel's own convention: numeric results get no `t` attribute, string results get `t="str"`, and unused rows carry `t="str"` with an empty value, exactly as a recalculated sheet would. The patched-parts set grows from two to three (product sheet, shared strings, payload sheet); everything else stays byte-identical. openpyxl is now imported by the generator but only ever to *read* the template's lookup tables — never to write.

**Verification hardened**, since this failure was invisible to every check that existed: `verify_cartup_sheet.py` now compares payload_hidden row *n−1* against product row *n* for name, both SKUs, stock, price and both image columns; requires the six dropdown columns to hold numeric ids; asserts no data past the last product row; fails on cached `#ERROR!`/`#N/A`/`#NAME` in the payload (the signature of a spreadsheet round-trip); and prints `payload_hidden (what CartUp actually imports): 29/29 rows carry values`. Proved by negative test — reverting just the payload part to the template's uncomputed state produces **377 failures**, where the previous verifier passed clean.

Output is now 0.60 MB (was 0.58; the cached values add ~21 KB), 29/29 rows, all 16 required fields, verifier exits 0.

## Homepage first impression (decision #94)

Reported as two bugs — the hero loads a default variation then swaps, and the page looks empty for the first few seconds. Both came from one root cause plus one design gap.

The root cause: the prerender crawl serves the built app on `127.0.0.1:4183` and that origin isn't in the API's CORS allowlist. Verified directly — the API returns 200 but omits `Access-Control-Allow-Origin`, so the browser discards every response. The build therefore baked a homepage with the **lime default hero and a dashed "Hero image" placeholder** while the live setting is `photo-fullbleed` with a real image, and it silently shipped all four policy pages as empty shells. That baked file is what Vercel actually serves for `/` (real files beat the `app.html` rewrite), so the wrong hero was the first thing every visitor saw. Fixed by proxying the crawl's API calls through Node's fetch via `page.route()` — Node isn't subject to CORS, so no backend change and nothing new exposed in production. 4/8 routes became 8/8, and the policy pages went from empty shells to ~18KB of real content.

The design gap: `HeroSection` defaulted an unknown `variant` to lime rather than treating unknown as its own state. Since the variants are different components at different heights, that made the swap a layout shift too. It now reserves space instead of guessing, and the three sections that returned `null` while loading (shelf, spotlight, testimonials) do the same — distinguishing "still loading" from "genuinely empty", which is the same distinction.

What the measurements changed: the fix I expected to be last turned out to matter most. After baking settings in, a timeline sample still showed the hero painting at 110ms, being replaced by the full-page spinner from 217–520ms, then returning — because `React.lazy` suspends for a render pass even when the chunk is already preloaded, and `createRoot` wipes the prerendered DOM. Making HomePage the one eager route removed it: hero at 82ms and never disappears; on throttled 3G the time with no hero fell from ~1840ms to ~80ms. The main bundle shrank from 198KB to 116KB as Rollup restructured around it.

Two things were checked rather than assumed. Fonts: all eight carry `font-display: swap`, so they never blocked text paint — left alone rather than adding preloads for a problem that didn't exist. And the `localhost:5173` canonical in `dist` turned out to be the same class of bug as the CORS one: the script read `process.env.VITE_SITE_URL`, which Node never populates from `.env`, so it fell back to the production origin while the bundle carried localhost. Reading `.env` the way Vite does fixed it — and immediately made the existing "refuse to bake local canonicals" guard fire correctly on local builds.

Trade recorded with the merchant: settings are baked at build time, so for well under a second after changing the hero in admin a visitor may see the previous one before the live fetch corrects it, and the baked copy refreshes on the next deploy.

## 2026-08-05 — Search Console indexing: the prerender had been dead in production

Google Search Console flagged four exclusion reasons for diecastbd.com on 28 Jul (alternate-canonical, noindex, 404, redirect). The merchant's constraint was explicit: fix it without migrating to Next.js.

I diagnosed against the live site rather than the repo, which turned out to matter — the cause was not the SPA architecture but a build step that had been failing silently for months. `curl` on `/`, `/about`, `/faq`, `/shop`, `/privacy-policy`, a real product and a real brand returned **the same 4067 bytes every time**: one generic `<title>`, and no `<link rel="canonical">` anywhere. To the crawl that happens before JS renders, all 48 sitemap URLs were the same page, which is exactly what "Alternate page with proper canonical tag" means. The `content-disposition` header settled it — `/` served `dist/index.html`, everything else served `filename="app.html"` — so no per-route files had ever been produced. Reading `scripts/prerender.mjs` found two independent swallows: `chromium.launch()` sat in a `try/finally` with no `catch`, escaping to `main().catch()` → `process.exit(0)`, and each route had its own `catch { log('skip') }`. The build went green either way.

Rather than fix Playwright I removed it. Everything failing here is head-level, and a head is a string, so the rewritten script fetches the API with plain Node and splices tags in — 48/48 routes in ~8 seconds instead of ~3 minutes, with no Chromium download in the deploy. Route discovery reads the backend's own `/sitemap.xml`, so the prerendered set and the sitemap can't drift apart. The formulas live in new shared `src/lib/seo/` modules imported by both React and the build script, which is what makes baked and rendered heads structurally identical instead of identical-by-review.

The subtle part was hydration. react-helmet-async v3 on React 19 renders metadata as ordinary elements that React *appends* — it never removes what's already in `<head>` — so naive baking gives every page two titles, two canonicals and two Product JSON-LD entities, and Google may discard an ambiguous canonical outright. One line in `main.jsx` strips `[data-prerendered]` before the first render, handing the head from the snapshot to React. `verify-hydration-parity.mjs` proves the handoff in a real browser; it needed its own static server because `vite preview` SPA-falls-back `/faq` to `index.html` and isn't a faithful stand-in for Vercel.

Four more real defects surfaced while verifying, each confirmed live before fixing: `/share-image` was returning a hard 404 while sitting in `og:image` on every page; `/index.html` was a live 200 duplicate of the home page; `api.diecastbd.com` had no robots.txt at all, so a JSON 404 told crawlers to take everything; and the sitemap advertised two QA pages, `/demo` and `/qa-blocks`.

The judgement call worth recording is robots.txt. It was `Disallow`-ing precisely the routes we needed *out* of the index — and that was preventing their removal, because Google has to be allowed to fetch a URL to see the `noindex` on it. Those rules are gone, replaced by `X-Robots-Tag` plus a rendered meta, with the reasoning written into the file so it isn't undone. The same fix on `NotFoundPage` was only safe once every caller learned to tell a real 404 from a transient failure: four components rendered it on *any* query error, so one API blip would have deindexed live products, brand pages and all four policy pages. That guard, not the `noindex`, was the risky part of this change.

Verified: 48/48 routes baked with distinct titles and canonicals; product pages carrying live `Product`/`Offer` JSON-LD; parity confirmed in Chromium with exactly one of each tag; soft-404s and private routes rendering `noindex` while `/shop` correctly renders none; frontend 105/105, backend 121/121, lint clean.

Left for the merchant, deliberately: unpublish `/demo` and `/qa-blocks` in Admin → Pages, upload a real 1200×630 share image, and set `PRERENDER_STRICT=1` on Vercel. Not done here: product slugs still regenerate on title change with no redirect, and unknown URLs still return HTTP 200 rather than a real 404.

Consequence accepted and written into the context snapshot: a product added in admin serves the generic shell until someone redeploys the frontend, so a redeploy is now part of the catalogue-change routine. Real 404s: leave unknown URLs at HTTP 200 + `noindex`, which is the right call precisely *because* rebuilds stay manual — narrowing the catch-all rewrite would hard-404 a product created between builds for real customers, not just crawlers.

## Reports ↔ orders sync, and the test-data purge (decision #95)

The merchant reported that Reports showed revenue for dates before their first real order, and asked that deleting an order remove its data from the report.
