# DiecastBD — Project Plan

Living architecture document for DiecastBD v1.0 — a premium, collector-focused diecast e-commerce platform for Bangladesh (Hot Wheels Premium + MINI GT now, more brands later). This file reflects the **current, as-built state** of the project, kept current as phases complete. For a chronological account of what happened and when, see `docs/log.md`.

---

## 1. Business Context

- **Brand positioning:** premium/luxury/minimal — "Apple, Porsche," not a toy shop. Dark theme, large product photography, restrained lime-green accent.
- **Current brands:** Hot Wheels Premium, MINI GT. Planned future brands: Tarmac Works, Kaido House, Inno64, Pop Race, Tomica Limited Vintage, Auto World.
- **Market:** Bangladesh. Currency: BDT (৳). Language: English only for v1.0.
- **Source of truth for inventory:** `docs/Inventory.md` (32 real SKUs, July 2026 purchase batch) — imported via `backend/src/seeds/`, never hand-typed into the frontend.
- **Payment:** Cash on Delivery (COD), plus manual bKash "Send Money" (System 4, post-launch) — customer sends payment to an admin-configured merchant number/QR outside the app and types the resulting Transaction ID at checkout; there's no live bKash merchant API/gateway integration, an admin verifies manually via `bkashTransactionId` on the order. A real gateway integration remains deferred until real bKash sandbox merchant credentials are available.

---

## 2. Tech Stack (as implemented)

**Frontend:** React 19, Vite, `react-router` v8 (no `react-router-dom`), Tailwind CSS v4, shadcn/ui (primary component layer, Radix-based) + DaisyUI (scoped to Rating/Steps/Loading only), Framer Motion, Embla Carousel (+ autoplay plugin), React Hook Form, Zod, Zustand (+ persist middleware for guest cart / recently-viewed), TanStack Query, Axios, React Hot Toast, React Helmet Async, Lucide React, Tiptap (`@tiptap/react` + `@tiptap/starter-kit`, System 9 — the admin CMS page-content editor, isolated to that one code-split admin route). Testing: Vitest + React Testing Library + jsdom (Phase 12).

**Backend:** Node.js (ESM), Express 5, MongoDB Atlas, Mongoose 9, Firebase Admin SDK, `jsonwebtoken`, Multer, Cloudinary SDK, Zod, Helmet, `express-rate-limit`, Morgan, CORS, Compression, Dotenv, `cookie-parser`, Resend, `node-cron` (nightly analytics rollup + hourly stale-reservation release), `bcrypt` (unused — Firebase owns credentials, no passwords stored locally), `sanitize-html` (System 9 — strips admin-authored CMS page HTML down to an explicit tag allow-list server-side, on save). Testing: Vitest (Phase 12).

**Notable version-driven deviations from the original plan** (see §7 for details): custom NoSQL-sanitize middleware (Express 5 breaks `express-mongo-sanitize`), custom `req.query` handling in validation middleware (Express 5's `req.query` is an uncached getter), `returnDocument: "after"` instead of deprecated Mongoose `new: true`.

## 5. API Reference (as built)

Base path `/api/v1`. Envelope: `{ success, data, meta? }` / `{ success: false, message, errors? }`. Every write route: `authenticate` → `authorize(role)` → `validate(schema)` → controller → (admin mutations) `auditLog`.

|---|---|

| Users (self) | `PATCH /users/me`, `DELETE /users/me` (soft-deactivate) · admin: `GET /admin/users` (search/filter by role/isActive), `GET /admin/users/:id`, `PATCH /admin/users/:id` (name/phone/isActive), `PATCH /admin/users/:id/role` (**admin-only**, not staff — guards: can't change own role, can't demote the last remaining admin) |

## 6. Frontend Architecture

- **Design system:** dark theme is a fixed brand identity choice, not a toggle — single `:root` palette in `index.css`, no light-mode variant. shadcn/ui is the primary primitive layer; DaisyUI covers only Rating/Steps/Loading. All page-width/padding logic lives in one `<Container>` component (see §7 — this was a real bug fix, not a preemptive abstraction).
- **State split:** Zustand for client-only state that has no server counterpart (guest cart, recently-viewed, auth session mirror). TanStack Query for everything that comes from the API. Nothing server-authoritative lives in Zustand.
- **Auth state:** `useCurrentUser()` (TanStack Query) is the source of truth; `authStore` (Zustand) mirrors just `{status, role}` for synchronous route-guard reads, always written from the query result — never fetched independently.
- **Cart duality:** one `useCart()` hook presents an identical interface whether the visitor is a guest (Zustand + localStorage) or logged in (server API) — components never branch on auth state. `CartMergeOnLogin` (mounted once at the app root) drains the guest cart into the server cart the moment login state flips.
- **Routing:** `react-router` v8 Data Router (`createBrowserRouter`). Layouts: `PublicLayout` (header/footer), `AuthLayout` (centered, no chrome), `AdminLayout` (sidebar). Guards: `ProtectedRoute` (any authenticated user), `RequireRole` (admin/staff only).

## 7. Key Architectural Decisions & Deviations

Flagged explicitly as they were made, not silently — this section is the running record.

1. **`OrderItems` embedded, not a separate collection.** Order line items are always read with their order, never queried independently, and must snapshot product state at purchase time so later edits/deletion never corrupt order history.
2. **`Cart` collection added** (not in the original spec list) — guest carts are client-only; logged-in carts need a server home independent of the `User` document to avoid write contention on auth-critical data.
3. **`Analytics` scoped to business rollups, not raw event tracking** — built in Phase 9 as `AnalyticsDaily`, computed nightly from Orders/Products/Users. Traffic/behavior analytics is intentionally out of scope — that's what GA4/Plausible are for.
4. **shadcn/ui + DaisyUI split**, not either/or — see §6.
5. **Express 5 compatibility fixes:**
   - `express-mongo-sanitize` reassigns `req.query` wholesale, which throws under Express 5 (`req.query` has no setter). Replaced with a custom middleware that mutates objects in place.
   - `req.query` in Express 5 is an **uncached getter** — it re-parses the raw query string on every access, so mutating the object it returns is silently discarded. The `validate()` middleware now shadows the property on the request instance via `Object.defineProperty` instead.
   - Mongoose 9 deprecated `findOneAndUpdate`'s `new: true` in favor of `returnDocument: "after"` — updated throughout.
6. **Mass-assignment fix:** `validate()` originally stripped unknown fields from the *validated result* but left them on `req.body` itself, letting a smuggled `"role": "admin"` ride through `PATCH /users/me` and self-promote a customer. Fixed at the middleware level (body is now fully replaced with validated data) and defense-in-depth in the controller (explicit field whitelist).
7. **Self-service profile CRUD landed in Phase 2**, admin user-management (list/search/role-change) deferred to Phase 10 alongside the admin UI that will consume it — building the API without the UI it's tested against would ship untested surface area. Role changes get their own dedicated endpoint (not folded into general profile update) so they can carry their own safety guards (can't demote yourself, can't demote the last admin) and their own audit-log action type.
8. **Stock reservation lifecycle** (Order module): `reservedStock` holds inventory for pending/unconfirmed orders without touching `stock`. Crossing into a "committed" status (`confirmed` and beyond) converts the hold into a permanent `stock` decrement (`InventoryLog` type `sale`). Cancelling before that commit just releases the hold (`release`); cancelling after commit restores the stock (`adjustment`). All of this runs inside a MongoDB multi-document transaction (Atlas clusters are replica sets even on the free tier, so this is available) — inventory/money correctness isn't a place to cut corners. **Generalized into a full 3-bucket state machine in System 7** (post-launch) — see decision #37; every status now maps to exactly one of `reserved`/`committed`/`released`, and `transitionOrderStatus` handles all six possible cross-bucket moves, not just the original one-directional `pending → confirmed → cancelled` path.
9. **Coupon math centralized** in `coupon.service.js` (`findValidCoupon` + `calculateDiscount`), shared by both the preview endpoint (`POST /coupons/validate`) and authoritative order creation — the discount calculation can never drift between preview and checkout.
10. **Transactional email uses a light-background template**, not the site's dark theme. Dark-mode HTML email renders inconsistently (sometimes illegibly) across clients that force their own color scheme — universal legibility wins over 1:1 brand-theme parity for this one surface.
11. **No fabricated content, ever.** Testimonials seed empty (frontend hides the section until real ones exist) rather than shipping fake customer quotes; social links/contact info stay blank rather than guessing at a real phone number or handle.
12. **`Container` component** (Phase 6): nine sections had independently hand-rolled "centered max-width content with padding," split between two subtly different nesting patterns that only diverge once the viewport exceeds the max-width. Consolidated onto one component so the bug class can't recur.
13. **bKash deferred**, COD-only for v1.0 checkout — real bKash sandbox merchant credentials require a business account the user doesn't have yet. The `Order` schema already carries `paymentMethod`/`paymentStatus`/`bkashTransactionId`, so wiring it up later is additive, not a rework.
14. **Stale-reservation release job** (Phase 9): a `pending` order older than 48 hours (never confirmed — customer abandoned COD or admin never actioned it) is auto-cancelled hourly by `releaseReservedStock.cron.js`, which reuses the existing `transitionOrderStatus` release path (`actorId: null` marks it system-initiated) rather than a bespoke stock-release code path — one lifecycle implementation, not two.
15. **`OrderStatusStepper` is one shared component** (`components/shared/`, built on the DaisyUI `steps` primitive reserved for this in Phase 0 §6) rendered on both the customer order-detail page and the admin order-detail page — the fulfillment flow (`pending → confirmed → packed → shipped → delivered`, or a terminal `cancelled`/`refunded` state) is one visual language, not two independently maintained progress indicators.
16. **Admin dashboard revenue chart is hand-built SVG**, not a charting library — the prescribed stack has no chart dependency, and the dashboard needs exactly one chart (single-series daily revenue line/area), which doesn't justify pulling in a general-purpose charting library. Follows the project's dataviz conventions: one hue (brand primary, since it's a single series — no legend needed), thin 2px line, hover crosshair + tooltip, recessive gridlines.
17. **Role changes are their own endpoint** (`PATCH /admin/users/:id/role`, admin-only — staff, who share every other `/admin/users` route, are explicitly excluded via a second `authorize("admin")` check on just this route), exactly as scoped in the Phase 0 addendum: guards against self-demotion and demoting the last remaining admin, both enforced server-side so the dashboard can never be locked out of.
18. **Coupon codes are immutable after creation**; the update endpoint doesn't accept `code`. Changing a distributed code would silently break every customer who already has it — deactivating and issuing a new code is the correct fix, not an edit. Deletion is similarly blocked once `usedCount > 0` (delete would erase real usage history); deactivation is the only path for a used coupon.
19. **`LOW_STOCK_THRESHOLD` extracted to `config/constants.js`**, shared by the analytics rollup (Phase 9) and the new inventory admin view (Phase 10) — two independent definitions of "low stock" would have been a real (if quiet) bug the moment one got tuned without the other.
20. **Manual stock adjustments are blocked from dropping `stock` below `reservedStock`** — reducing total stock below what's already promised to pending orders would silently break the reservation invariant the whole checkout/fulfillment lifecycle (Phase 8) depends on. The admin sees a clear error naming the reserved quantity rather than a generic validation failure.
21. **"Media" scoped into the Settings editor, not a standalone library.** The original Phase 0 folder sketch listed a separate `admin/media/`, but nothing in the spec needs a general asset browser beyond what per-product Cloudinary upload (Phase 3) and hero-banner images (Phase 10) already cover. `POST /admin/settings/upload-image` returns a Cloudinary `{url, cloudinaryId}` for the editor to attach to a hero slide and save with the next full settings PATCH, rather than a slide-index-addressed endpoint that would race against reordering.
22. **Reports reuses the Phase 9 `AnalyticsDaily` history**, not a separate reporting backend — `GET /admin/analytics/daily` already has everything a daily report needs; the Reports page adds a date-range picker and a client-side CSV export over the same data the Dashboard chart already fetches.
23. **Contact form is a stateless email relay, not a persisted collection.** The original DB schema list never included a `ContactMessage` model, and adding one (plus the admin inbox UI it would need) is real scope the spec never asked for. `POST /contact` sends straight to the store's configured contact email (`Settings.contactInfo.email`, falling back to the first `ADMIN_EMAILS` entry) via the existing Resend integration. Unlike order-confirmation email — a nice-to-have on top of an order that already succeeded — delivering the message *is* the entire point of this endpoint, so a missing recipient or a Resend failure throws and surfaces as a real error instead of silently reporting "Message sent."
24. **FAQ content is admin-editable (`Settings.faqs[]`), not hardcoded.** Same pattern as testimonials/social links since Phase 4: no real FAQ copy existed to ship, so the page renders an empty state pointing to Contact until the admin adds real questions through the Settings editor — never fabricated placeholder policy text.
25. **`components/ui/accordion.jsx` added in Phase 11** — reserved for exactly this (PDP specs/FAQ) back in the Phase 0 shadcn/DaisyUI split, but never actually generated until the FAQ page needed it. Hand-written against the project's `radix-ui` unified-package convention (matching `switch.jsx`/`separator.jsx`), not the shadcn CLI, since `tw-animate-css` (already imported project-wide) ships the `accordion-down`/`accordion-up` keyframes it needs.
26. **Session revocation via `tokenVersion`, not a token store** (Phase 12). Instant session kill (deactivation, demotion, log-out-everywhere) is done with a per-user counter stamped into each JWT (`tv`) and checked on refresh — a leaked/rotated refresh token whose `tv` is stale is rejected. This buys instant revocation of the long-lived (30-day) refresh credential with zero new infrastructure (no Redis/DB token blocklist). The access token stays deliberately stateless (no per-request DB hit), so its ≤15-min window is unchanged — an accepted tradeoff, since the refresh path is where durable access actually lives. Refresh also rotates *both* tokens now, not just the access token.
27. **`trust proxy` set to `1` in production, and admin auto-promotion requires `email_verified`** (Phase 12 hardening). The proxy trust is a deployment necessity behind Render/Railway (secure cookies + correct rate-limit keying); it's `1` (one known hop) rather than `true` so a client can't spoof `X-Forwarded-For` to dodge IP limits. The email-verified gate closes a narrow admin self-escalation path (Firebase doesn't require email verification for email/password sign-ups by default).

### Post-launch feature systems (business requirements doc)

A separate 11-item requirements doc was reviewed and approved as a full architecture review before any code — see the plan file's Guest Checkout → Homepage "See All" breakdown for the complete per-system review. Decisions from System 1 (the only one shipped so far):

28. **Guest Checkout extends `User`, not a parallel "Customer" model.** `firebaseUid`/`email` became optional + sparse-unique (existing accounts are unaffected — no data violates the looser constraint), `phone` gained a non-unique index. A repeat guest is matched by email first, then phone — deliberately "find first match" application logic (`findOrCreateGuestUser` in `user.service.js`), not a DB-level unique constraint on phone, since a hard constraint there would 500 on a plausible shared-household-number collision.
29. **`createOrderFromCart` and the new `createOrderFromItems` share one `buildAndSaveOrder` + `reserveStockForItems` core** (`order.service.js`). Guest checkout (and, later, Buy Now — System 3) can't read a server `Cart` document the way logged-in checkout does, since guest carts are Zustand/localStorage-only and never touch the server — so they send `items[{productId,qty}]` directly in the request body instead. Extracting the shared core means the stock-reservation/coupon/shipping/order-creation math can never drift between the cart-based and items-based paths, mirroring the project's existing centralized-discount-math precedent (decision #9).
30. **`optionalAuthenticate` middleware, not a second copy of `authenticate`.** Reads the JWT cookie if present and sets `req.user`, but (unlike `authenticate`) never rejects the request if it's absent — used only on the two routes that must serve both guests and logged-in users (`POST /orders`, `POST /coupons/validate`); every other authenticated route is completely untouched.
31. **Order confirmation is a separate public page (`OrderConfirmationPage`, `/order-confirmation`), not a loosened auth check on the existing order-detail route.** A guest has no session to authenticate an order-number lookup against, but making that lookup fully public would let anyone enumerate `orderNumber`s (a readable, guessable format, not a bearer secret) and read other customers' addresses/phone numbers. Instead, the create-order response already contains the full order — `CheckoutPage` passes it straight through via router state to a new page that only ever renders from that state (never fetches), used by guests *and* logged-in customers alike right after checkout. The authenticated `/orders/:orderNumber` (order history, revisited later) is completely unchanged. Both pages render the same `OrderReceipt` component so they can't visually drift apart.
32. **Shipping is a list of named zones (`Settings.shippingZones[]`), not a flat fee** (System 2). Matches the requirement's Inside/Outside Dhaka split without hardcoding zone names into the schema — an admin can rename/add/remove zones freely via the same `useFieldArray` editor pattern already used for `faqs[]`. `buildAndSaveOrder` looks up the fee by matching `shippingZone` (a name, sent from checkout) against `Settings.shippingZones`; a miss falls back to a `0` fee rather than throwing, so a stale/renamed zone can never hard-block a checkout — it just ships free instead of failing the order outright. The existing free-shipping-threshold override still applies uniformly on top of whichever zone fee is looked up. Live `Settings` document and its Mongoose index needed a one-time migration (native-driver `$unset` for the orphaned `shippingFee` field — Mongoose's schema-aware `$unset` silently no-ops on fields no longer in the schema; `User.syncIndexes()` to actually rebuild the `firebaseUid`/`email` indexes as sparse, since a schema-level `sparse: true` change doesn't retroactively alter an already-existing index).
33. **Buy Now is a pure frontend feature, zero backend changes** (System 3). It reuses System 1's `createOrderFromItems` + `optionalAuthenticate`/items-branching in `order.controller.js` verbatim — the controller already routed any request carrying `items[]` onto that path regardless of auth state, so a *logged-in* Buy Now just needed the frontend to start sending `items` too (previously only guests did). `BuyNowButton` (new, `features/products/components/`) never calls `useCart()`/`addItem()` — it hands `{product, qty: 1}` to `/checkout` via router `state` only, so a customer's real cart is provably untouched by a Buy Now purchase (verified by curl: placed a Buy Now order for a logged-in user with an unrelated item already in their server cart, confirmed the cart still held only its original item afterward, and the order contained only the Buy Now product). `CheckoutPage` reads `location.state?.buyNowItem`; when present it sources `items`/`subtotal` from a single normalized line item instead of `useCart()`, so `OrderSummary`, `CouponInput`, and the stock-issue guard all work unmodified against either source. Losing router state on refresh degrades to the existing empty-cart redirect (or the real cart, if non-empty) — an accepted tradeoff, not a bug, since Buy Now is an ephemeral one-click path.
34. **Manual bKash, not a live payment gateway** (System 4) — matches the requirement literally: the customer sends money to an admin-configured number/QR (`Settings.bkashConfig`, reusing the existing `imageSchema`/upload-image endpoint verbatim) outside the app and types the resulting Transaction ID at checkout; an admin verifies it manually (surfaced on both the admin and customer order-detail views) and updates `paymentStatus` themselves — there is no gateway callback, no `paymentStatus` automation. `bkashTransactionId` is conditionally required via a Zod `.refine()` on `createOrderSchema` (and mirrored in the frontend `checkoutSchema`) — only when `paymentMethod === "bkash"`, so COD orders are completely unaffected. `Order.paymentStatus`/`bkashTransactionId` needed no schema change at all — both fields were already built into the model in Phase 8 (decision #13) anticipating exactly this.
35. **`profitMargin` is a virtual, computed, never stored** (System 5), mirroring the existing `availableStock` virtual's exact pattern — resolves automatically wherever `costPrice` is already `.select("+costPrice")`ed. Returns `null` (not `0`) when `costPrice` is unset/unselected — an admin needs to tell "0% margin" apart from "cost unknown," and the public storefront (which never selects `costPrice`) gets a harmless `null` rather than a fabricated number. Both the Sale badge and Cost/Profit tracking requirements turned out to be mostly already built (Phase 6/Phase 3 respectively) — System 5 closed the two real gaps: the PDP was missing the Sale badge `ProductCard` already had, and the admin products table had no Cost/Profit/Margin columns despite `costPrice` already being a fully wired, editable field. **Revised same day per explicit user correction:** originally computed off list `price` only ("a catalog-level metric, doesn't dip during a sale"); the user asked instead for Price/Profit/Margin to reflect the *live* selling price — margin now uses `salePrice` whenever the item is actually on sale (same `salePrice != null && salePrice < price` check used everywhere else in the codebase), falling back to `price` otherwise. The admin products table's Price column now also shows the sale price with the original struck through (matching `ProductCard`'s existing storefront pattern) instead of always showing list price, and gained a Sale badge next to the title. The Sale badge itself was also restyled off `variant="destructive"` (a muted/low-contrast red, not actually eye-catching) to a solid `bg-amber-400 text-background` — a warm, high-contrast accent distinct from the lime-green "New" badge, applied consistently on `ProductCard`, the PDP, and the new admin table badge.
36. **`homepageSections` toggle map covers the sections `HomePage.jsx` actually renders, not the plan review's original list.** The architecture review's draft section list included a "faq" toggle, but no FAQ section is ever rendered on the homepage (FAQs live on their own `/faq` page) — building a toggle for a section that doesn't exist would be dead config, so the shipped map instead has one entry per real section: `hero` (+ `autoplay`/`autoplayInterval`), `collectorPicks`, `featuredProducts`, `brandsStrip`, `newArrivals`, `whyChooseUs`, `collectorPromise`, `testimonials`, `instagramFeed`, `newsletter`. Every toggle defaults to `enabled: true`, and the frontend's `isEnabled()` check also defaults to `true` when a key is missing entirely — so an un-migrated or partially-saved document can never accidentally hide a section. Implemented as a gate at each section's call site in `HomePage.jsx` (`{isEnabled("x") && <Section .../>}`) rather than editing every section component's internal render guard — same visual outcome, smaller and lower-risk diff (one file instead of seven). Hero's Embla `Autoplay` plugin delay, previously a hardcoded `6000`, is now `autoplayInterval * 1000` passed at hook-init time; Embla doesn't hot-reload a running plugin's delay after mount, so a live admin edit takes effect on the visitor's next page load, not instantly mid-session — consistent with how every other Settings-driven value already behaves in this app (nothing here supports true live-reload without a refresh).
37. **Order status transitions are a full 3-bucket state machine, not the original one-directional pending→confirmed→cancelled path** (System 7 — unrestricted status changes). Every status maps to exactly one stock bucket — `reserved` (pending: held via `reservedStock`, nothing decremented), `committed` (confirmed/packed/shipped/delivered: `stock` permanently decremented, no hold), `released` (cancelled/refunded: no claim on stock at all) — and `transitionOrderStatus` (`order.service.js`) now handles all six possible cross-bucket moves, not just the original forward ones. The terminal lock (`if (TERMINAL_STATUSES.includes(...)) throw`) is gone entirely; the only remaining guard is same-status (`pending → pending` etc.), which still 400s. **The original architecture review's plan text for the `committed → reserved` delta was wrong** (`{stock: -qty, reservedStock: +qty}`) — worked through concretely with real numbers before writing any code: undoing a commit must restore *both* fields (`{stock: +qty, reservedStock: +qty}`), or `availableStock` silently drifts further wrong on every confirmed↔pending bounce. The review also hadn't accounted for reverting *out of* a released status at all (`cancelled`/`refunded` → anything else) — naively reusing the existing reserved→committed branch for that direction would drive `reservedStock` negative, since a released order's hold is already fully cleared to zero. **`released → reserved` and `released → committed` are the only two directions that re-check availability** (the same atomic `findOneAndUpdate` + `$expr` compare-and-reserve pattern `reserveStockForItems` already uses) — every other direction trusts the order's existing hold/commit and applies its delta unconditionally, exactly as the original code did. This isn't optional defense-in-depth: another customer can genuinely buy up stock while an order sits cancelled, and un-cancelling it without checking would oversell. Verified with a real disposable order and a real competing order: reverting a cancelled order back to `pending` after a second order consumed all the freed stock correctly returns a 409, not a silent negative-stock write. **Verification approach:** curl-scripted the full transition matrix against a real product on the dev database (not a mocked/unit-tested state) — all six cross-bucket transitions, the same-bucket no-op case, the same-status guard, and the exact `confirmed → pending → cancelled` repro that was independently confirmed as a real latent bug in the pre-System-7 code (closed by this fix) — 24 assertions, all passing, cleaned up and restored to baseline afterward. `stockBucket()`, the pure classification function every branch dispatches on, is exported and covered by a dedicated Vitest unit test (`order.stockBucket.test.js`) — the six-branch `$inc`/atomic-guard logic itself stays curl-verified rather than adding new integration-test infrastructure (`mongodb-memory-server` or similar), consistent with how every other transaction-heavy path in this project has been verified so far.
38. **Dashboard Analytics ships Orders/Revenue with a date-range filter; "Total Visitors" is skipped, per explicit user confirmation** (System 8). Re-presented the architecture review's own recommendation before starting (traffic tracking needs a new event-ingestion endpoint, bot filtering, session dedup — a genuinely different category of infrastructure this project deliberately scoped out in favor of GA4/Plausible, decision #3) — user confirmed skip. `GET /admin/analytics/daily` gained an optional `startDate`/`endDate` query pair (takes priority over `days` when both are present); the existing `days` param and every current caller (`ReportsPage.jsx`'s 7/30/90 presets) are completely unchanged. Dashboard's new range picker (Today/Last 7 days/Last 30 days/Custom range) reuses the same `Select` pattern already proven in `ReportsPage.jsx`. **"Today" deliberately does not call the new range endpoint at all** — the nightly rollup hasn't computed `AnalyticsDaily` for the current day yet (same reason `GET /admin/analytics/summary` already computes today live instead of reading the stored table, decision documented on the `AnalyticsDaily` schema row), so a `startDate=endDate=today` range query would come back empty despite real sales existing. "Today" instead reuses the already-fetched `summary.today` object directly — it has the exact same row shape (`{date, revenue, ordersCount, ...}`) `computeDailyRollup()` produces, so it slots into the same chart/stat-sum logic as any other row with no special-casing needed downstream.
39. **CMS Pages is a new `Page` collection with its own module, not a `Settings` extension — and About/Contact/FAQ deliberately stay exactly as they are** (System 9). `Settings` is a singleton; Pages is inherently a collection of independent documents, so forcing it into `Settings` would be a real modeling mismatch (unlike every other post-launch extension in this batch, which correctly reused `Settings`). About/Contact/FAQ are richer than a flat content page (Contact has a live form, FAQ renders `Settings.faqs[]` as an Accordion) — migrating them onto the new generic `PageView` component was flagged as a scope question at review time and deliberately left undone; this system only ships the 4 net-new pages (Terms/Privacy/Refund/Shipping-Policy) the requirement actually asked for. **User chose Tiptap for the admin rich-text editor and to seed all 4 pages empty** (both explicitly confirmed before starting, per the review's own flagged blockers) — `isPublished: false` and `content: ""` for all four; an admin writes and publishes real copy later via Admin → Pages, same "no fabricated content" precedent as testimonials/bKash config/social links. Admin-authored HTML is sanitized **server-side on save**, not client-side on render (`page.controller.js`, `sanitize-html` with an explicit tag allow-list matching exactly what `@tiptap/starter-kit` produces) — verified against a real XSS attempt: a `<script>` tag was stripped entirely and a `javascript:` URL in an `<a href>` had its `href` attribute removed, while a legitimate relative link passed through untouched. Public `GET /pages/:slug` 404s for anything not `isPublished` — verified directly, then verified again after publishing that the same slug returns the sanitized content. Tiptap (`@tiptap/react` + `@tiptap/starter-kit`, ~427KB, ~134KB gzipped) is isolated entirely to the code-split admin page-editor route (`PageFormPage.jsx`) and never reaches the public storefront bundle.
40. **Header/Footer link management extends `Settings` (not a new collection) — the plain link lists only, not the cart/auth-state icons or announcement bar**, per the requirement's own "keep the interface simple" scoping (System 10). No `logo` override field either, despite being sketched in the original review — the requirement was specifically about link management, and adding upload/override machinery for something that's a static brand asset today would be unrequested customization. `navigation.headerLinks[]`/`footerLinks[]` have no separate `order` field — array position is the order, matching every other list field already on this document (none of them support explicit reordering either, only add/remove). **A live-DB migration was required, not just a seed update** — unlike a fresh install, the *already-existing* Settings document doesn't get `$setOnInsert` seed values applied to a newly-added field; Mongoose's schema-level `default: []` on the array sub-fields made `GET /settings` **appear** to already have `navigation` populated (an in-memory hydration artifact — confirmed empty on the raw stored document), which would have made the header/footer go visibly blank the instant this code deployed. Migrated the live document to hold exactly what `PublicLayout.jsx`/`Footer.jsx` already had hardcoded (one "Shop" header link; About/Contact/FAQ/Shipping-Policy/Refund-Policy/Privacy-Policy/Terms-Conditions footer links, matching System 9's just-added legal-page links too) — verified via curl before and after, confirming the migration changed nothing about what a visitor would actually see. Both `PublicLayout.jsx` and `Footer.jsx` additionally fall back to their original hardcoded values in-code if `navigation.headerLinks`/`footerLinks` is ever empty, so an admin accidentally deleting every link can't leave the site with no navigation at all.
41. **"See All" is two new optional props on the existing shared `ProductCarouselSection`, not a new component** (System 11 — the smallest, lowest-risk system in the whole batch, zero backend/DB/API changes). `seeAllHref`/`seeAllLabel` (default `"See All"`) render a plain text link next to the existing prev/next carousel buttons, only when `seeAllHref` is passed — every other consumer of this shared component (`ProductDetailPage.jsx`'s "Related Products"/"Recently Viewed") is completely unaffected since they never pass the new prop. All three homepage product carousels (Collector Picks, Featured Products, New Arrivals) point at plain `/shop`, per the requirement's literal reading ("navigate to the main Shop/Store page") rather than a per-section filtered deep-link — the architecture review had flagged this as an open question with that literal reading as the default if the user didn't specify a preference otherwise.

## Production deployment — Vercel (both apps)

Full runbook + env vars + DNS + troubleshooting table in `docs/DEPLOYMENT.md`. This decision records the load-bearing choices.

50. **Both apps deploy to Vercel as two projects from one repo; the backend is a serverless function on the `api.diecastbd.com` *subdomain*, not a bare `*.vercel.app` host.** Topology: `diecastbd.com` (apex, canonical) → frontend project (Root Directory `frontend`, Vite); `www` → 308 redirect to apex; `api.diecastbd.com` → backend project (Root Directory `backend`, Express serverless); DNS on Vercel nameservers (Vercel authoritative). **Four things had to be true, each learned by hitting the failure first:** (a) **jose ESM** — `firebase-admin` → `jwks-rsa` `require()`s ESM-only `jose@6` and crashes with `ERR_REQUIRE_ESM`; pinned via `overrides: { "jose": "^4.15.9" }` (CJS-compatible) in `backend/package.json`. (b) **Serverless entrypoint** — Vercel's modern `functions`/`rewrites` config left framework auto-detection on, which grabbed the Express app in `src/app.js` and demanded a default export (`Invalid export found in module src/app.js`); switched `backend/vercel.json` to legacy `builds`/`routes` pinning the single `api/index.js` handler (connect-DB-then-delegate), which disables auto-detection entirely — **do not re-add `functions`/`rewrites`**. As belt-and-suspenders `src/app.js` also `export default app` + a `process.env.VERCEL`-gated `connectDB()` middleware, so it's a valid handler even if served directly (local/tests unaffected — no `VERCEL` env). (c) **Same-site cookies** — auth is httpOnly cookies with `sameSite:"none"; secure:true`; with the backend on `die-castbd-backend.vercel.app` those were cross-site third-party cookies that browsers block (Safari always, Chrome increasingly) → **401 on every authed route** and the admin dashboard couldn't load. Fixed with zero code change by moving the backend to `api.diecastbd.com` (same registrable domain as the storefront → first-party cookies). `CLIENT_URL` stays the single canonical frontend origin (`https://diecastbd.com`) — it's used for CORS *and* sitemap/email links, so it can't be a list; a new optional `CORS_ORIGINS` env var adds extra credentialed-CORS origins (e.g. `http://localhost:5173`) without corrupting those links. (d) **Frontend lockfile** — `@fontsource-variable/*` were declared in `package.json` but unresolved in `package-lock.json`, failing `npm run build` (and Vercel `npm ci`); reconciled with `npm install`. Cron jobs run via Vercel Cron over HTTP to `/api/v1/cron/*` (guarded by `CRON_SECRET`), not `node-cron`. `VITE_` vars are build-time-inlined, so changing `VITE_API_BASE_URL` requires a frontend **rebuild**, not just a redeploy of the same build.

51. **Hero copy is admin-editable per variant, with the shipped design copy as the render fallback.** Previously only the hero's floating highlight card was editable; the badge/headline/subtitle/both CTAs/footnote were hardcoded per variant in `HeroSection.jsx`. Added `homepageSections.hero.content.{limeShowroom,darkSpotlight,photoFullbleed}` to the settings model + Zod validation — one content object per visual style (only the selected `variant` renders, but all three are editable so switching styles keeps each one's own copy). Every field is **optional**; `resolveCopy()` in `HeroSection.jsx` trims each value and falls back to that variant's `DEFAULTS` (the existing shipped copy) when blank, so an un-migrated/un-edited document — including live production, which has no `content` field yet — renders byte-identical to before. Verified against the live backend: production's contentless hero rendered the exact default copy. CTAs now use the editable `primaryCtaLink`/`secondaryCtaLink` (default `/shop`). **Mobile-first cleanup:** dropped the separate mobile/desktop copy strings (title stays two lines on desktop via a responsive `<br>`, one value everywhere) so admins edit one field, not two. **Alignment fix:** the hero hard-coded `max-w-[1440px]` while every other section uses `Container`'s `max-w-[1360px]` — 80px wider, so its edges bled past the sections below; changed to `1360px`, and normalized the dark-spotlight panel's oversized `md:p-[72px_64px]` to `md:p-16` (matching lime) and trimmed `photo-fullbleed` height `560px→520px` so the hero sits in proportion. The shared `highlightCard` path was deliberately left in place (not moved under `content`) to avoid orphaning the live card data. All new settings fields are additive/optional — safe for the running Vercel/Render deployment, but the backend must be redeployed for the new admin fields to persist.

52. **Every storefront text input renders at 16px on mobile to kill iOS Safari's zoom-on-focus; bottom-sheet modals gained a max-height + internal scroll.** The reported "typing breaks the whole layout" bug on mobile was iOS Safari's mandatory auto-zoom when a focused `<input>`/`<textarea>` has a computed `font-size < 16px` — it zooms the entire page and pans it sideways, leaving the site visibly "broken" and stuck zoomed. The custom storefront fields were all `text-[13.5px]` (and the auth fields `text-sm`/14px), so every one triggered it. Fix is CSS-only and mobile-scoped: each custom input/textarea now leads with `text-base` (16px) and restores its design size behind `md:` (`md:text-[13.5px]` / `md:text-sm`) — desktop is pixel-unchanged. Covered the four shared `inputCls` constants (AddressForm, AccountPage, checkout `parts.jsx`, ContactPage), the auth `authInputCls`, and the standalone inputs (ShopPage search, CartDrawer/cart CouponRow, footer NewsletterForm, RestockAlertDialog). The shadcn `Input`/`Textarea` primitives (admin) were already `text-base md:text-sm`, so admin was never affected. Separately, the two bottom-sheet modals (`ResponsiveModal`, `RestockAlertDialog` — the only two `side="bottom"` sheets) had `h-auto` with no height cap or scroll container, so with the keyboard open the lower form fields sat under it unreachable; added `data-[side=bottom]:max-h-[92dvh]` + `data-[side=bottom]:overflow-y-auto` at the `SheetContent` primitive level (scoped to the bottom side only — the right-side CartDrawer already scrolls its own item list and is untouched) plus `interactive-widget=resizes-content` on the viewport meta so the layout viewport shrinks to the visible area when the keyboard appears. Verified in the mobile preview: the shop search input computes to `16px` at 375px width. All changes are frontend-only CSS — no backend, no schema, safe for the live deployment (needs a frontend rebuild/redeploy to take effect since it's build-time CSS).

53. **Product images fill their placeholder (`object-cover`) instead of floating inside padding (`object-contain p-[X%]`).** The user reported product photos sitting inside visible whitespace across the storefront — the images were `object-contain` with percentage padding (`p-[4%]`–`p-[6%]`), which letterboxes the photo inside the box. Switched every product-photo surface to `object-cover` so the image fills the whole placeholder: `ProductCard`, `FeaturedSpotlight` (both images), `ProductGallery` main + thumbnails, `CartLineItem`, `WishlistCard`, `CheckoutSummary`, `OrderReceipt`, `RestockAlertDialog` summary, and the three `ShopByShelf` tiles. Two surfaces were intentionally left `object-contain`: the `ProductGallery` **lightbox** (full-screen zoom must show the whole piece uncropped) and the `PaymentMethods` **bKash QR** (cropping a QR breaks it). **ShopByShelf caveat:** its tiles render `brand.logo`/`category.image`; the current catalog stores framed promo/product imagery there so cover fills correctly, but a genuinely transparent brand *wordmark* logo would crop under cover — revisit if the brand-logo field is ever populated with a bare transparent logo. Also removed the now-dead `isLogo` prop from `ShopByShelf`'s `Tile`. Frontend-only CSS — no backend/schema change, safe for the live deployment; needs a frontend rebuild/redeploy. Verified: lint + build clean; in the running preview all 20 product images on the home page compute to `object-fit: cover` (0 `contain`) at both mobile 375px and desktop.
